# Batch curriculum production

The canonical catalogue, learning schema and assessment service remain the source of truth. One canonical subtrack owns shared teaching and progress across every referencing track and role. New batches add original authored data, not a separate student framework or generated duplicate course records.

The internal `career/curriculum/learning/wave1/` helpers assemble explicitly authored lesson and question rows. They do not substitute a generic explanation or question template for subject-specific teaching. Candidate files stay unregistered until complete. Existing courses and historical banks are preserved. Human-edited runtime drafts take precedence over repository defaults, as before.

Use the following recoverable workflow:

1. Run `npm run curriculum:wave -- plan --limit 20 --output /tmp/next-wave.json`. The queue prioritizes the unfinished junior backend requirements and shared prerequisites. `--prefer id,id` can prioritize another complete pathway. Every selected prerequisite appears first; already authored subtracks are omitted.
2. Assign each canonical ID to one author. Workers may write separate candidate files and private helpers. Integrate shared manifests, verification artifacts and inventories sequentially. Preserve canonical module/objective IDs and link existing prerequisites instead of duplicating lessons or student evidence.
3. Author complete lesson prose, examples and distinct MCQs in the existing schema. Candidate courses live at `career/curriculum/learning/wave1/<id>.js`; new comprehensive banks at `career/curriculum/questions/wave1/<id>.js`. Existing banks are reused where suitable. All new items remain draft.
4. Run `npm run curriculum:wave -- check --ids id,id --execute --output /tmp/wave-checkpoint.json`. The checker loads candidates without altering the registry or database, runs structural and assessment checks, checks exact/near-duplicate teaching, verifies form coverage and option balance, and executes supported examples through the existing resource-limited network-isolated verifier. There is no unsandboxed fallback.
5. Correct or quarantine failures. Inspect quality warnings, especially ambiguous questions, option-length clues, near-duplicates and misleading examples. Automated checks cannot prove prose truth or a single defensible answer; those still need educational review. Use `--resume /tmp/wave-checkpoint.json` to reuse code evidence only when both the complete course and bank fingerprints match. Reruns replace checkpoint artifacts atomically and never import student records.
6. Add only accepted canonical IDs to the current curated wave manifest. `learning/registry.js` aggregates immutable earlier waves with the current wave; do not append a new execution to a historical manifest. Candidate source files retain their stable paths under `learning/wave1/` and `questions/wave1/`. Registration reuses historical banks and keeps every new bank outside automatic historical approval. Requiring modules is idempotent; no database migrations or duplicate imports occur.
7. Run `npm run validate:career:learning -- --source-roots /tmp/source-roots.json --require-sources --output career/curriculum/learning/verification.json`. The roots JSON maps official repository names to pinned local checkouts. References must match their recorded Git commit and actual source bytes. Do not claim public page availability or deployed behavior from this check. The existing per-source CLI flags remain supported. `--reuse-verified` reuses only exact worked-code/expected-output/language hashes, while structural checks and source-byte verification still run. Official AWS HTTPS captures are a separate source kind with matched capture manifest, URL, HTTP status, date and SHA-256; they are never labeled immutable Git revisions.
8. Run `test/career-wave.test.js` with the existing targeted suite. It tests every curated course's draft gates, guided reading, lesson quizzes, module checkpoints, failed-skill remediation, fresh final forms, direct assessment and shared evidence. Browser tests use only synthetic accounts and disposable stores. Never publish test approvals in normal startup.
9. Produce an isolated inventory with `npm run inventory:career:learning -- --output /tmp/inventory.json`. Report authored, structural, example-verified, human-reviewed and published counts separately. A fully authored mandatory pathway still needs actual human review, assessment publication and its role-final gate.
10. Build private HTML with `npm run review:career:learning -- /workspace/echolens-audit/review-wave`. Bundle keyed questions, sources, exact verification results, test logs, screenshots, pending IDs and a review patch outside `public/`. Review output refuses public paths, including symlink aliases. Commit verified drafts locally. Push, merge and deployment require explicit authorization.

The checkpoint and next-wave queue are repository artifacts, not a background job. Work stops when the execution session ends. Resume from the saved checkpoint and exact pending inventory; do not regenerate accepted content or claim all 132 subtracks are complete prematurely.

Optional example profiles execute native JavaScript (`javascript`), pandas (`python-pandas`) and FastAPI (`python-fastapi`) in isolated, read-only runtimes. They do not expose the workspace/home or inherit credentials. Standard Python/SQL limits remain unchanged; optional profiles have explicit bounded address-space/heap settings. Missing package runtimes fail closed; there is no unsandboxed fallback. The known development package runtime is not required merely to serve lesson text. Changed examples need an available matching verifier before approval.

For a focused staff bundle, run `node scripts/build-career-pathway-review.cjs junior-backend-developer /workspace/echolens-audit/junior-backend-review`. This includes exactly the canonical prerequisite-expanded mandatory packages, example hashes, objective/question mappings, duplication findings and an SME checklist; it never approves or publishes the role final.
